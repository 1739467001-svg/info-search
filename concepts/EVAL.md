# 💡 EVAL（LLM 评测 / Evals）

> 整理日期：2026-09-27 ｜ 类型：概念解读 ｜ 关联：`relations.md`
> 一句话总结：**EVAL 是给大语言模型应用写"测试"——用一组固定用例和评分标准，重复、客观地衡量 AI 输出好不好。对 AI 开发者来说，它是把"感觉还行"变成"可验证、可回归"的唯一途径，相当于 LLM 应用的单元测试。**

---

## 1. 名词解释（准确版）

**教科书级定义（多来源交叉核对）：**

> **Hamel Husain（AI 评测实践权威）：** evals 是"超越 vibe check（凭感觉验收）、针对自家用户真实任务定制的测试与评测系统"。
>
> **OpenAI Evals（官方开源框架）自述：** "评估 LLM 与 LLM 系统的框架，同时是一个开源基准（benchmark）注册表"。
>
> **Simon Willison（知名 AI 独立开发者）：** 评测是"可靠工程与 YOLO 式开发的分水岭"，他自述 60–80% 的精力投入写评测。

**通俗拆解：** 普通软件有单元测试——写几行断言，跑一遍就知道改坏没有。但大模型的输出是**概率性、不稳定的**，同一个问题可能答得好也可能答得烂，没法用"结果等于 xx"这种硬断言判断"答得好不好"。EVAL 就是补上这个缺口：**用一套"问题＋评分标准"反复检验 AI 的表现，让你改了提示词、换了模型之后，能确凿地知道它变好了还是变坏了。**

**关键词口径说明（别搞混）：**
- **eval / evals**：泛指"评测"——既指一条评测用例，也指整套评测体系。
- 和 Python 内置 `eval()` 函数（执行字符串代码）**完全无关**，只是同名。
- 和 **benchmark（基准测试）** 是两回事："大考卷" vs "月考"（见第 4 节辨析）。

**为什么对 AI 开发者特别重要：** 大模型应用没有"编译报错"这种保底——把提示词改坏了，线上开始胡说八道的占比可能只有百分之几，肉眼根本看不出来。EVAL 是唯一能让你**放心迭代**的手段，也是"评测驱动开发"（eval-driven development）的主循环：写用例 → 跑评测 → 分析失败 → 迭代修复。

## 2. 核心拆解（EVAL 由什么组成）

一个最小可用评测系统 = 三件套：

| 组件 | 是什么 | 例子 |
|------|--------|------|
| **数据集** | 一组测试用例：输入 + 期望输出 | 「用户问：退货政策是什么 → 期望回答包含"30 天无理由"」 |
| **运行器** | 把用例逐个喂给模型/应用 | 调 API、跑 LLM 应用、跑 Agent |
| **评分器** | 判断每个输出好坏 | 见下方 4 种方式 |

**评分方式（由简到繁）：**

1. **确定性判定（gradable）**：硬规则判断——回答是否包含关键词、是否匹配正则、是否是合法 JSON、工具调用是否有效。最快、最可靠。
2. **LLM-as-a-judge（大模型当裁判）**：让 GPT-4 这类模型按评分标准给输出打分（0-10 或分级）。适合"开放性好坏"这类见仁见智的判断。
3. **专用指标**：典型如 RAG 指标——faithfulness（回答是否被检索内容支持，即有没有编造）、context precision（相关片段是否排得靠前）、context recall（相关片段是否都被检索到）。
4. **人工评估**：人工检视，作最终裁决，通常用于抽检与争议案例。

> **gradable vs non-gradable**：能写硬断言的叫 gradable，主观需要模型或人工判分的叫 non-gradable。评测设计第一课就是分清：**能写断言的字段用断言，不能断言的才上 LLM 裁判**（来源：Promptfoo 文档 expected-outputs）。

## 3. 来龙去脉（演变时间线）

| 时间 | 事件 | 标志 |
|------|------|------|
| 2002–2004 | 传统 NLP 指标时代 | BLEU（机器翻译）、ROUGE（摘要）——纯文本重合度指标 |
| 2020 | 大模型基准开始 | MMLU 发布（57 学科考试式选择题） |
| 2021 | 代码评测出现 | HumanEval（让模型写代码，用自动纠错验证） |
| 2022 | "大考卷"底蕴时代 | BIG-bench（204 个任务）、斯坦福 HELM（多维度系统性评测） |
| 2023 | **应用层评测框架爆发** | OpenAI Evals 开源、Promptfoo、RAGAS（RAG 专用指标库）、DeepEval、LangSmith 评估器上线；MT-Bench 提出 "LLM-as-a-judge" 方法论 |
| 2023.10 | Agent 评测开端 | SWE-bench：用 2,294 个真实 GitHub issue 测 AI 改 bug，当时最强的 GPT-4 也只能解决 1.96% |
| 2024–2026 | 评测成为 AI 工程标配 | 评测驱动开发成主流；Agent/工具调用评测兴起（SWE-bench 成为标配考题） |

**演变主线：** 从"算文本重合度"（BLEU）→ 到"测通用实力"（MMLU）→ 再到"测真实工程能力"（SWE-bench）→ 最终落到"测你自己的业务"（自建 evals）。前两者是公共考卷，后者才是你日常迭代用的。

## 4. 概念辨析

| 概念 | 相同点 | 关键区别 |
|------|--------|----------|
| **EVAL（自建评测）** | 都是测量 LLM 质量 | 针对**自家具体应用**的用例集；用作回归测试与迭代 |
| Benchmark（基准） | 都是测量 LLM 质量 | 通用公开考卷（MMLU/HELM），测的是公告实力与排行榜，不贴近你的真实用户 |
| 单元测试（传统） | 都是防止代码退化 | 单元测试断言直白（结果 == 期望值），EVAL 的结果判断本身就需要模型/人机 |
| Vibe check（凭感觉测试） | 都在验证 AI 好不好用 | 主观、不可重复；EVAL 可重复、可量化、可回归 |

## 5. 例子与类比

- **类比：** 评测之于 LLM 应用，如同血小板之于体检——每个星期测一次，指标异常就知道出事了；也是"月考"：考卷固定，才能对比这个月有没有进步。
- **生活例子（RAG 问答机器人）：** 线上机器人回答 "退货政策是 30 天" 错了两次。你把这两次错误记进评测集，未来每次改检索逻辑后跑一遍：如果新逻辑把这两条修好、其他用例没退步 → 可以上线。这就是"错误沉淀为回归用例"。
- **行业项目例子：** LangSmith 线上发现问题（用户反馈的坏回答）→ 自动/手动沉淀为数据集 → 离线跑评测 → 修好后再回到线上。是"线上问题反哺线下回归"的最典型闭环。

## 6. 争议与局限（多视角）

| 视角 | 主要观点 | 代表证据/来源 |
|------|----------|--------------|
| 对 LLM-as-judge 的质疑 | 裁判有系统性偏见：回答位置靠前/靠后会被错误偏袒，模型偏爱自己模型，内容写得长更容易高分 | 学术测试：调换两个回答的先后顺序改变了 80 次中的 66 次结论（2305.17926）；MT-Bench 论文点了位置、冗长、自我增强三类偏好 |
| 对公开基准的质疑 | 基准已饱和+可能已污染训练数据，分数与真实任务脱节；Simon Willison 表示更愿意看失败样例而非基准分数 | 基准榜单上新模型差距只有个位数；"满分"未必是好消息 |
| Goodhart 定律 | 指标一旦被优化就无法可靠测量——过度拟合评测集，拿到高分但真实业务变差 | "70% 通过率比 100% 更健康"（Simon Willison）——满分常意味着考卷过拟合 |
| 维护成本 | 写评测上手难、更新数据集费时、LLM 裁判调用费钱 | Hamel 等人在实践中反复指出评测是巨大的投入且经常做不好 |

## 7. 如何用它（给 AI 开发者的实操路径）

**落地四步（业界公认做法）：**

1. **先 5–10 条用例起步**：把你应用"最重要的行为"人工想出 5–10 条用例（不必等线上数据），先跑起来，再扩到几百条。
2. **确定性判断优先于专家裁判：** 能断言工具的用断言，不得已再上 LLM 打分，并配合**人工抽检**防止"裁判瞎打分"。
3. **线上错误全部沉淀成回归用例：** 每个修掉的线上问题都是评估集的新增成员（Anthropic 的 agent 开发三步论也是同源逻辑："先从简单提示词开始 → 建立全面评测 → 必要时才加 Agent 复杂层"）。
4. **评测跑进 CI：** 每次改动自动回归（Promptfoo 就是为此而生的），否则评测只是写着看的。

**常见误区：**
- 一上来就追公开基准分数 → 与你的业务脱节；
- 只测正确性、不测格式/安全/多轮交互；
- 追求 100% 通过 → 大概率是评测集过拟合，"70% 通过率 + 失败用例可见"才健康；
- 评测没有进 CI → 形同虚设。
